# Данные сборки DOCX

Эти файлы готовит Codex после настройки и исследования проекта. Пользователь заполняет YAML и отвечает на вопросы; JSON вручную ему создавать не нужно.

## Содержание

temp/report-content.json содержит `blocks` в порядке документа. Заголовки должны в точности совпадать с temp/report-plan.json. Титул и содержание в blocks не входят: сборщик берет temp/title.docx и добавляет настоящий TOC.

Поддержанные блоки:

- `{"type":"heading","text":"Точное название из плана"}` — уровень и стиль из плана.
- `{"type":"paragraph","text":"Связный подтвержденный текст."}` — Times New Roman 14, 1,5, отступ 1,25 см, по ширине.
- `{"type":"figure","number":"2.1","title":"Название","file":"screenshots/selected/screen.png","width_mm":160}` — реальное изображение; ширина не больше области печати, пропорции сохраняются. Перед блоком нужна ссылка `(Рисунок 2.1)`, после — связный законченный текст.
- `{"type":"figure","number":"2.2","title":"Название","status":"pending-manual","blank_lines":5}` — пустая область из абзаца с переводами строк и обычной подписью. Нужна соответствующая запись manifest и нейтральная ссылка перед областью. Не делать белую картинку вместо пустой области.
- `{"type":"table","caption":"Таблица 3.1 - Название","headers":["№","Что проверялось","Ожидаемый результат","Результат"],"rows":[["1","Описание","Ожидание","Фактический результат"]]}` — подпись сверху; ячейки 12 pt, одинарный интервал, по ширине. Данные примера не являются проведенным тестом.
- `{"type":"page_break"}` — устаревший блок: допускается только непосредственно перед заголовком уровня 1 и игнорируется сборщиком. Новые входы его не используют. В остальных местах сборщик отклоняет блок; принудительные разрывы ради точки и перед подразделами запрещены.

Формулы, продолжения таблиц и другие сложные элементы при необходимости дополнять средствами Word/python-docx с соблюдением spec. Сборщик задает новую страницу заголовкам уровня 1 и автоматический поток остальному тексту. Перед подразделом он добавляет один пустой абзац, кроме случая сразу после любого заголовка уровня 1. Заголовки удерживаются с последующим текстом. Повторный рендер после правок обязателен; проверять минимум 70% на каждой странице основной части, включая концы разделов. Пустая область pending-manual не увеличивает заполненность.

Для таблицы можно задать widths_mm — список ширин граф в миллиметрах с общей шириной не больше 170 мм; графу «№» делать узкой. Пустая область содержит только невидимый пробел и переводы строки; это не изображение и не текстовый placeholder. Размер пустой области проверять по PDF, при необходимости менять blank_lines.

Команда:

```text
python tools/build_report.py --title temp/title.docx --content temp/report-content.json --plan temp/report-plan.json --output temp/draft.docx
```

Титул должен содержать одну секцию без конечного разрыва страницы. Поля и номер страницы первой секции скрываются, основная часть начинается после TOC. Для нового отчета применять официальные поля ко всем секциям. Не использовать сборщик для регенерации защищенной пользовательской версии.

## Доказательства рисунков

screenshots/manifest.json — текущий машиночитаемый manifest; screenshots/manifest.md — необязательная читаемая сводка. Не копировать данные из старого отчета.

```json
{
  "input_signature": "Значение из текущего temp/setup.json",
  "figures": [
    {
      "number": "2.1",
      "caption": "Рисунок 2.1 Название",
      "section": "Точный заголовок раздела из плана",
      "status": "observed",
      "file": "screenshots/selected/screen.png",
      "scenario": "Фактически выполненные действия",
      "source": "Подтверждающие исходники",
      "log": "temp/evidence/ui.log"
    }
  ]
}
```

Для `pending-manual` не задавать file; добавить `expected_state` и `blocker`. Лог фиксирует попытку запуска/получения снимка и блокер. Исходники подтверждают наличие соответствующей функции. Номер, полная подпись и section должны соответствовать документу. Статус observed не присваивать только по наличию исходников или процесса.

Для новых observed-снимков добавить `capture_review`: `cursor` (`neutral` либо `intentional-hover`), `ready` и `readable` (true после фактической проверки), `note` (куда убран курсор или зачем показано наведение). Эти поля фиксируют осмотр, а не заменяют его. Старый manifest без этих сведений требует повторного просмотра оригиналов; не заполнять их автоматически без проверки.

В план также записать `input_signature` из текущей настройки. Валидатор сравнивает его с manifest. Перед повторным использованием доказательств повторно выполнить prepare_report и сравнить input_signature: при отличии заново проверить относящиеся к изменениям сценарии и пересоздать manifest. Результаты тестов, команды и границы проверок хранить в temp/evidence/; не вносить факты отдельного проекта в общие docs/.

Структурная проверка принимает `pending-manual` только для существующей подписи и пустой области в указанном разделе, со сценарием, источником, логом, причиной и ожидаемым состоянием. Такой результат требует вставки настоящего снимка и повторной проверки перед сдачей.
