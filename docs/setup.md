# Настройка новой работы

Начать с config/student.yaml и выборочной инвентаризации project/ и references/. Сначала определить сведения из материалов, затем одним коротким сообщением спросить недостающее. До необходимых ответов не писать отчет. Данные, даты, подтверждения и тесты примеров или temp/archive-original к новой работе не относятся.

## Вопросы перед началом

1. ФИО, группа, специальность, учреждение и город - только отсутствующие сведения.
2. Вид работы, модуль и код практики, название, даты начала/окончания, руководители. Имена из примера предложить для подтверждения.
3. Тема, путь проекта и индивидуальное задание. Если файла нет, запросить текст, сохранить в temp/assignment.md и указать путь в config. Не составлять задание по чужому отчету.
4. Основной current-example при нескольких файлах и предпочтительный previous-report для стиля; без прошлых отчетов применять writing-style.md.
5. Ручные условия запуска, демонстрационная учетная запись, разрешение на вход и допустимые действия с тестовыми данными. Секреты не сохранять в config, отчете и логах. Для правок определить последний DOCX и защищенные части.

Стек и функции установить по исходникам; не заставлять пользователя переписывать README. Новые частные пожелания хранить в temp/session.md; общие правила менять только по поручению. Все накопленные требования spec и writing-style обязательны, не спрашивать разрешение на правильное оформление.

## Входы и среда

`python tools/prepare_report.py --json temp/setup.json --summary` проверяет YAML, даты, пути и доступность среды; код 2 означает незавершенную настройку. Сначала читать краткую сводку и все issues, затем нужные поля полного JSON. Скрипт не устанавливает ПО, не запускает приложение и не доказывает работоспособность Word. Python брать из workspace dependencies, иначе Python 3.10+ с requirements.txt; недостающие зависимости устанавливать изолированно, не менять bundled runtime. После подтвержденных ответов заполнить config и повторить проверку.

В setup.json сохраняются SHA-256 config, правил, инструментов, выбранных примеров, задания и исходников проекта. Скрипт сравнивает предыдущий setup.json **до перезаписи**: cache содержит match/changed/cold/invalid и списки added/changed/removed. inputs_match=true означает совпадение корректных завершенных снимков входов, а не выполненный запуск, тест или визуальную проверку.

## Работа с контекстом

- При cache.inputs_match=true можно читать существующие извлечения и карту исходников, привязанные к этой input_signature; при changed/cold/invalid заново проверить материалы и зависимые выводы. Старые артефакты без подтвержденной привязки не использовать. Журналы/снимки сверять с текущим manifest и состоянием приложения; изменения среды, зависимостей или данных требуют новой проверки сценариев даже при совпадении исходников. Архив не является входом новой работы.
- Прочитать spec и writing-style полностью перед написанием. В том же контексте не перечитывать неизмененные инструкции; после потери контекста восстановить нужные правила из файлов. Детали content-format и навыков загрузить на соответствующем этапе. Ничего не исключать из обязательных проверок.
- Искать rg с исключением .git, .vs, зависимостей, сборок, temp и output; известные артефакты temp читать напрямую. Исходники исследовать по задачам; карту «функция → файл/символ → факт» хранить в temp/evidence/source-map.md с текущей input_signature. Обращаться к исходникам для неподтвержденных деталей, а не повторять весь анализ.
- Извлечения сохранять в temp/extracted/: inspect_docx.py/inspect_pdf.py с --json, --text и --summary. После извлечения записать текущую input_signature и пути в temp/extracted/index.json; без такой привязки кэш не использовать. Чтение plain text дешевле полного JSON форматирования. Сканированный PDF обязательно смотреть визуально; пустое извлечение не означает отсутствие требований. Выбранные пути фиксировать в config.
- Для prepare_report, inspect_docx, inspect_pdf, validate_report, check_revision_layout и check_subsection_conclusions использовать --json FILE --summary: полные данные остаются на диске, все ошибки и предупреждения выводятся. Сводка не заменяет чтение текста, итогов, доказательств и просмотр всех страниц. Другие полные журналы сохранять в temp/, выводить ошибки и путь к файлу, не скрывать код завершения.
- В temp/session.md кратко сохранять текущий этап, input_signature, пути артефактов, нерешенные вопросы и ограничения. Не копировать туда правила и весь отчет. Состояние помогает продолжить работу, но не является доказательством выполнения.

## План

Создать temp/report-plan.json по текущему примеру: сохраненный TOC, реальные заголовки и титул. Исправлять явные опечатки без изменения смысла. Сопоставить с официальными требованиями и заданием; неоднозначности уточнить до написания. Требуемая в примере технология не доказывает ее применение.

```json
{
  "body_start": "Первый заголовок основной части",
  "headings": [
    {"text": "Первый заголовок основной части", "level": 1, "role": "assignment"},
    {"text": "1 НАЗВАНИЕ РАЗДЕЛА", "level": 1, "role": "section"},
    {"text": "1.1 Название подраздела", "level": 2, "role": "subsection"},
    {"text": "2 ТЕСТИРОВАНИЕ", "level": 1, "role": "testing"},
    {"text": "ЗАКЛЮЧЕНИЕ", "level": 1, "role": "conclusion"}
  ]
}
```

Это схема, не готовая структура. Перечислить точные заголовки основной части по порядку; body_start совпадает с первым. Содержание перед основной частью в headings не входит. Роли: assignment, introduction, section, subsection, guide, testing, conclusion, appendix. guide может иметь level 1 или 2; итог обязателен при level 2. testing содержит две таблицы черного и белого ящика; отсутствие в примере уточнить, не отменять правило. Нумерация определяется новым примером, лимит 25 страниц и все правила spec сохраняются.

## Сборка и исправления

Порядок работы задан в generate-practice-report/SKILL.md, проверки - в validate-practice-report/SKILL.md. Формат блоков для build_report.py - docs/content-format.md. Текст и доказательства готовит Codex, сборщик их не придумывает. Оформление полностью задано в docs/report-spec.md, повествование - docs/writing-style.md; примеры не ослабляют эти правила. При правках продолжать последнюю пользовательскую версию с baseline и защищенными страницами, не регенерировать из старого title/content. Итог требует структурных проверок, полного рендера и визуального просмотра каждой страницы.
