# Настройка новой работы

Начинать с config/student.yaml и инвентаризации project/ и references/. Сначала определить, что уже известно из материалов, затем одним коротким сообщением спросить только недостающие сведения. Не писать отчет до получения необходимых ответов. Данные, даты, подтверждения и тесты примеров или temp/archive-original не относятся к новой работе.

## Вопросы перед началом

1. ФИО, группа, специальность, учреждение и город — только отсутствующие сведения.
2. Вид работы, модуль и код практики, название, даты начала/окончания, руководители. Имена руководителей из примера предложить для подтверждения, не считать подтвержденными автоматически.
3. Тема, путь проекта и индивидуальное задание. Если файла нет, запросить текст, сохранить его в temp/assignment.md и указать путь в config. Не составлять задание по чужому отчету.
4. Основной current-example, если файлов несколько, и предпочтительный previous-report для стиля. Если прошлых отчетов нет, применять writing-style.md.
5. Ручные условия запуска, демонстрационная учетная запись, разрешение на вход и допустимые действия с тестовыми данными. Секреты не сохранять в config, отчете и журналах. При правках уточнить последний DOCX и защищенные части.

Стек и функции определить по исходникам. Не заставлять пользователя переписывать README. Все накопленные правила оформления обязательны; не спрашивать, нужны ли правильные интервалы и отступы. Новые частные пожелания сохранять в temp/session.md; менять общие правила только по поручению.

## Входы и среда

`python tools/prepare_report.py --json temp/setup.json` проверяет YAML, даты и пути, показывает пропуски и доступность библиотек/средств экспорта. Код 2 означает, что настройка не завершена. Python брать из workspace dependencies, если доступны, иначе использовать Python 3.10+ с requirements.txt. Скрипт не устанавливает ПО, не запускает проект и не доказывает работоспособность Word.

После ответов заполнить config и повторить проверку. В temp/setup.json сохраняются SHA-256 выбранных примеров, задания, правил и исходников проекта. Если входы изменились, заново извлечь измененные документы, пересмотреть план и доказательства. Выбранные пути записать в config, чтобы выбор был однозначен. Извлечения хранить в temp/extracted/. Сканированный PDF читать визуально; пустое текстовое извлечение не означает отсутствие требований.

## План

Codex создает temp/report-plan.json по выбранному current-example, включая сохраненный TOC и реальные заголовки/титул. Исправлять явные опечатки без изменения смысла. Сопоставить структуру с официальными требованиями и заданием; неоднозначности уточнить до написания. Требуемая в примере технология не доказывает ее использование в новом проекте.

```json
{
  "body_start": "Первый заголовок основной части",
  "headings": [
    {"text": "Первый заголовок основной части", "level": 1, "role": "assignment"},
    {"text": "1 НАЗВАНИЕ РАЗДЕЛА", "level": 1, "role": "section"},
    {"text": "1.1 Название подраздела", "level": 2, "role": "subsection"},
    {"text": "2 ТЕСТИРОВАНИЕ", "level": 1, "role": "testing"},
    {"text": "ЗАКЛЮЧЕНИЕ", "level": 1, "role": "conclusion"}
  ]
}
```

Это схема, не готовая структура новой работы. Все заголовки основной части перечислять с точными названиями в порядке документа; body_start совпадает с первым. Содержание находится перед основной частью и в headings не входит. Роли: assignment, introduction, section, subsection, guide, testing, conclusion, appendix. guide может иметь level 1 или 2; итог обязателен при level 2. testing — раздел с двумя таблицами черного и белого ящика. Его отсутствие в примере уточнить, не отменять правило двух таблиц. Нумерация определяется новым примером; лимит 25 страниц и все правила spec сохраняются.

## Сборка и исправления

С помощью documents skill, если доступен, подготовить temp/title.docx: только заполненный титул по текущему примеру, без его содержания/основной части и без завершающего пустого листа. Найти поля конкретного макета, заменить все ФИО, даты, модуль, тему и город. Не использовать номера абзацев чужого шаблона. Сверить с config и проверить визуально. Если skill недоступен, использовать python-docx и доступный Word/LibreOffice; обязательный просмотр всех страниц сохраняется.

tools/build_report.py принимает подготовленный титул, план и temp/report-content.json по docs/content-format.md. Текст и доказательства готовит Codex; сборщик их не придумывает. Формулы и другие неподдержанные сложные элементы добавлять как настоящие элементы Word отдельной правкой с теми же проверками.

Перед сборкой проверить содержание по writing-style.md: существенные средства и задачи записать в temp/technology-review.md; расхождения с заданием и ограничения исследования — в temp/evidence/discrepancies.md. Руководство объясняет действия с реальными элементами, данные и результат; проведенные тесты описываются в тестировании. Существенные расхождения уточнить до написания затронутых утверждений.

В новом DOCX основные разделы начинаются с новой страницы, подразделы продолжают текущую с одним пустым абзацем перед заголовком, кроме случая сразу после раздела. Не вставлять разрывы ради окончания страницы точкой: разрешено продолжение предложения. После окончательного экспорта выполнить check_revision_layout.py с --pdf, проверить 70% заполненности каждой страницы основной части и просмотреть каждую PNG. Подписанные пустые области не входят в заполненность. Несовместимость требований фиксировать в temp/layout-conflicts.md; без полного рендера, просмотра и разрешения конфликтов не объявлять отчет полностью проверенным.

При исправлениях работать с последней пользовательской версией и сохранить baseline в temp/revision/. Не регенерировать ее из title/content. При запрете менять титул/содержание передать первый заголовок текущего плана через -BodyStartHeading при Word-экспорте, сравнить защищенную часть и подогнать начала разделов под сохраненные номера. Подробности — report-spec.md и validate-practice-report/SKILL.md.
