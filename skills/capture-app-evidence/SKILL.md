# Capture app evidence

Прочитать [правила рисунков](../../docs/report-spec.md) и [config](../../config/student.yaml). Команды выполнять из корня workspace; проект изучать выборочно.

1. По штатным инструкциям определить тип приложения и зависимости. Восстановить зависимости, проверить окружение без раскрытия секретов, подготовить безопасную локальную БД/migrations/seed. Собрать и запустить компоненты в правильном порядке; команды, ошибки и readiness сохранить в temp/. Не менять внешнюю/рабочую БД без разрешения.
2. Вывести evidence plan из структуры отчета и реализованных сценариев: роли, списки, формы, операции и результаты. Задание не подтверждает наличие функции. Подготовить минимальные тестовые данные; процесс не доказывает работоспособность UI.
3. Web проверять доступной browser automation; desktop — native UI automation; mobile — эмулятором. Проверять состояние после действий. CLI и снимки исходников не заменяют проверку интерфейса.
4. Сохранять реальные оригиналы с понятными именами в screenshots/raw/, лучшие — в screenshots/selected/. Исключать посторонние окна/DevTools и перекрытие важных данных; не растягивать, не апскейлить и не дублировать снимки. Не использовать ImageGen/макеты.

   Перед каждым снимком после нажатия или открытия вкладки переместить курсор доступным API автоматизации в нейтральную область вне интерактивных элементов и данных. Дождаться исчезновения tooltip/hover, завершения загрузки и анимации; проверить состояние приложения. Затем снять и открыть оригинал: кнопки, подписи и данные должны читаться, важные элементы не перекрыты. Если автоматизация не умеет перемещать курсор, использовать безопасный доступный способ или зафиксировать ограничение, не утверждая выполнение шага. Намеренное наведение для объяснения функции снимать отдельно и пояснять в manifest. Сохранить фактический capture_review по content-format.md; при дефекте повторить снимок, не ретушировать интерфейс.
5. При блокере проверить безопасные альтернативы и записать причину. Если запуск/снимки недоступны, продолжить отчет по правилу пустых рисунков из spec, без фиктивных изображений и заявлений об успешном сценарии.

Создать новый screenshots/manifest.json по docs/content-format.md и читаемую сводку screenshots/manifest.md с колонками ниже. Связать доказательства с текущими входами из temp/setup.json; не использовать архивные наблюдения для другого проекта.

Если пользователь разрешил вход, использовать существующую демонстрационную учетную запись из учебного проекта и подтвердить открытие главного окна. Окно входа само по себе не доказывает авторизацию. Не обходить проверку пароля и не печатать учетные данные в отчете или логах. После входа получать снимки нужных разделов и проверять безопасные действия чтения. Карточки можно открыть и закрыть без сохранения; не создавать деловые записи только ради иллюстраций. Сохранять дерево наблюдений и результат каждого фактически выполненного сценария. Если отказ в авторизации остается, использовать предусмотренные пустые области.

номер и подпись рисунка | файл либо pending-manual | сценарий и его статус | раздел | подтверждаемый факт и источник | результат/блокер и лог

Для pending-manual указать, какое состояние пользователь должен снять вручную. Не отмечать невыполненные действия выполненными. Завершать только процессы, запущенные этим workflow.


Сводку выполненных тестов, команды, журналы и границы проверки хранить в temp/evidence/, а не в общих docs/. Не исправлять исходники приложения ради успешного отчета без поручения; безопасные настройки и изолированные тестовые данные не изменяют доказанность исходной реализации. Проверять доступность UI automation заново в текущей среде.
