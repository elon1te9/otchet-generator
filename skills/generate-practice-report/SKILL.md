# Generate practice report

Прочитать [настройку](../../docs/setup.md), [spec](../../docs/report-spec.md), [стиль](../../docs/writing-style.md) и [config](../../config/student.yaml). Команды выполнять из корня workspace. Все накопленные правила оформления обязательны для всех пользователей; сменными являются материалы, персональные данные и структура.

1. Провести настройку по setup.md: изучить доступные входы, задать недостающие вопросы, сохранить только подтвержденные данные в config. Проверить библиотеки requirements.txt в выбранном Python; недостающие зависимости устанавливать в отдельную среду, не изменяя общий bundled runtime. Выполнить tools/prepare_report.py --json temp/setup.json. При незавершенной настройке получить необходимые ответы. Не переносить подтверждения и имена из примера или архива.
2. Выбрать актуальный пример и образец стиля из config/инвентаризации. Извлечь документы в temp/extracted/, проверить сканированные страницы визуально. При совпадающих SHA-256 можно использовать текущие извлечения. Создать temp/report-plan.json по фактическому содержанию примера и заданию. Разрешить неоднозначности структуры до написания.
3. Выборочно изучить project.path: README, зависимости, точки входа, хранение данных, нужные обработчики. Использовать rg с исключением .git, .vs, зависимостей и сборок. Задание задает требования, а не доказывает реализацию. Установить фактический стек и функции; отсутствие БД не заменять придуманной БД.
4. Выполнить [capture-app-evidence](../capture-app-evidence/SKILL.md): попытаться собрать/запустить приложение по его инструкции, проверить сценарии, получить реальные снимки и новый manifest. При блокере продолжить по правилу пустых рисунков; успех без доказательств не заявлять.
5. Написать текст по текущему плану. Различать задание, исходную реализацию и выполненные проверки. Сопоставление утверждений с доказательствами хранить в temp/. Каждый подраздел завершить содержательным итогом «В результате», «В итоге» или «Таким образом». Руководство строить вокруг действий и экранов. Тестирование — две отдельные таблицы черного и белого ящика; тесты белого ящика выполнить на реальных неизмененных компонентах, сохранить код и результаты. Анализ кода не является выполненным тестом.
6. Использовать documents skill, если он доступен, либо локальные инструменты. Подготовить заполненный титул именно по текущему макету без фиксированных индексов чужого документа. Собрать DOCX через tools/build_report.py по docs/content-format.md или адаптировать документ с теми же стилями из tools/report_formatting.py. Сохранять настоящие TOC/PAGE и необходимые REF/SEQ. Не создавать фиктивные интерфейсы и изображения.
7. Выполнить [validate-practice-report](../validate-practice-report/SKILL.md) с --plan temp/report-plan.json. Проверить структуру, поля и весь рендер; исправить дефекты. Оставить итоговый DOCX в output/, черновики/QA в temp/. Перечислить pending-manual рисунки и ограничения проверки.

При исправлении существующего отчета сохранить последнюю пользовательскую версию в temp/revision/ и работать с ней, а не собирать ее из старого черновика. Определить защищенные части; отдельные стили основной части не должны менять титул/TOC. При запрете менять содержание сохранить его кэш, подогнать пагинацию под сохраненные номера и использовать -PreserveToc -BodyStartHeading с первым заголовком текущего плана. Выполнить сравнение с baseline и визуально проверить защищенные страницы. Не менять config по данным защищенного титула без поручения. Все отступы, интервалы, тире, подписи, окончание страниц и итоги проверять по spec и инструментам.
