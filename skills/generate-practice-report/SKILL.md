# Generate practice report

Начать с [setup](../../docs/setup.md) и config/student.yaml. Команды выполнять из корня workspace. Настройка, исследование, написание и проверка остаются обязательными; экономить повторное чтение и вывод, а не проверки.

1. Настроить текущую работу по setup: изучить входы, спросить только недостающие или неоднозначные данные и сохранить подтвержденные ответы в config. Выполнить `python tools/prepare_report.py --json temp/setup.json --summary`. Получить необходимые ответы при needs-input; проверить зависимости в выбранном Python, недостающие устанавливать изолированно. Для исправлений сначала сохранить последнюю пользовательскую версию в temp/revision/ и определить защищенные части; править ее, не пересобирать из старого title/content.
2. Извлечь выбранные документы в temp/extracted/ через inspect_docx.py или inspect_pdf.py с --json и --text. Сканированные PDF читать визуально. Повторное использование разрешено только после проверки входов по setup. Составить temp/report-plan.json по текущему примеру, кэшу TOC и заданию; разрешить неоднозначности до написания.
3. Выборочно изучить project.path: README, зависимости, точки входа, хранение данных и обработчики нужных сценариев. Сохранить компактную карту «функция → файл/символ → подтверждаемый факт» в temp/evidence/source-map.md. Исходники и задание не доказывают успешный запуск.
4. Выполнить [capture-app-evidence](../capture-app-evidence/SKILL.md): попытаться собрать/запустить проект, проверить сценарии и получить текущие доказательства. При блокере продолжить по правилу пустых рисунков из spec. Белый ящик выполнять на реальных неизмененных компонентах, сохраняя код, команду и результаты в temp/evidence/; анализ кода не является выполненным тестом.
5. Перед написанием полностью прочитать [spec](../../docs/report-spec.md) и [writing-style](../../docs/writing-style.md), если актуальные правила еще не прочитаны в этом контексте. Они обязательны для всех пользователей. Написать temp/report-content.json по текущему плану; соответствие утверждений доказательствам хранить в temp/. Проверить каждый абзац, полноту существенных средств в temp/technology-review.md и расхождения в temp/evidence/discrepancies.md. Существенные расхождения уточнить до затронутых утверждений. Требования к итогам, руководству, двум таблицам тестирования и границам проверки полностью заданы в этих документах.
6. Использовать documents skill, если доступен, иначе локальные инструменты. Подготовить temp/title.docx по текущему макету и config, без чужих полей, основной части и завершающего пустого листа; проверить визуально. Собрать через tools/build_report.py по [content-format](../../docs/content-format.md) и tools/report_formatting.py. Неподдержанные сложные элементы добавлять настоящими элементами Word с теми же проверками. Для правок продолжать работу в последнем пользовательском DOCX.
7. Выполнить [validate-practice-report](../validate-practice-report/SKILL.md) с текущим --plan. Исправить дефекты, проверить весь окончательный рендер и каждую страницу. Итоговый DOCX сохранить в output/, QA в temp/. Сообщить pending-manual и ограничения проверки; машинный pass не означает полностью проверенный отчет.
