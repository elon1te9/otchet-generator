# Validate practice report

Применять все правила [spec](../../docs/report-spec.md) и [writing-style](../../docs/writing-style.md); читать их полностью, если актуальная версия еще не прочитана в этом контексте. Использовать текущие config/student.yaml, temp/report-plan.json и manifest при рисунках/пустых областях. Команды выполнять из корня workspace; полные результаты сохранять с --json, в консоль выводить --summary.

1. Запустить tools/inspect_docx.py с --json и --text; читать извлеченный текст для проверки смысла, детали оформления из JSON по необходимости. Запустить tools/validate_report.py DOCX --plan temp/report-plan.json --json temp/structural-check.json --summary и tools/check_revision_layout.py с текущим --plan, --manifest при наличии и --json temp/layout-check.json --summary. Проверить все требования spec, включая те, которые не покрыты автоматикой.
2. Сверить титул с config и текущим макетом; исключить чужие данные. Проверить реальные TOC/PAGE и используемые REF/SEQ, скрытый номер титула, номера страниц. Сверить ссылки, подписи, порядок и качество рисунков с manifest и оригиналами, включая capture_review.
3. Прочитать весь основной текст и сопоставить утверждения с исходниками, логами и manifest. Удалить неподтвержденные утверждения либо фактически проверить их. Не допускать текстовых placeholders; пустые рисунки допустимы только по spec. Проверить temp/technology-review.md, связное объяснение средств и задач, простой учебный язык, пояснения терминов, содержательные итоги и границы тестирования. Руководство проверять отдельно по writing-style; расхождения хранить в temp/evidence/discrepancies.md, реальные ошибки выполненных тестов оставлять в тестировании. Сохранить результат чтения в temp/content-review.md.
4. Выполнить `tools/check_subsection_conclusions.py DOCX --plan temp/report-plan.json --json temp/conclusions-check.json --summary`. Прочитать последние абзацы из сохраненного JSON и проверить смысл каждого итога: вводные слова сами по себе не доказывают завершение темы.
5. Обновить поля и экспортировать окончательный DOCX/PDF:

```powershell
tools/render_docx_word.ps1 -InputDocx temp/draft.docx -OutputDocx output/report.docx -OutputPdf temp/render/report.pdf -UpdateFields
```

Если Word недоступен, использовать documents renderer с доступным LibreOffice. Проверить фактическое обновление полей; OOXML-коды этого не доказывают. При невозможности сообщить ограничение.

6. Проверить экспортированный DOCX обоими структурными валидаторами; передать окончательный PDF в check_revision_layout.py через --pdf. Рендерить **все** страницы через `tools/inspect_pdf.py PDF --json temp/render/pdf.json --render-dir temp/render/pages --summary`. Осмотреть каждую PNG, при проверке интервалов и пустот в исходном разрешении. Проверить весь spec: поля, титул/TOC/колонтитулы, рисунки, таблицы, формулы, переносы, начала разделов, заголовки и заполненность каждой страницы основной части. Зафиксировать страницы и замечания в temp/visual-review.md.
7. После исправлений повторить обновление полей, проверки и весь рендер с просмотром каждой страницы окончательной версии. Конфликты записать в temp/layout-conflicts.md с конкретными страницами и измерениями, как требует spec. Без PDF rendered_status=not-run; complete_verification=false и требования ручной проверки не отменяются машинным pass. Выдать DOCX, перечислить pending-manual и необходимость повторной проверки после вставки снимков. Код 2 при совпадающем manifest означает предусмотренные пустые рисунки, а не готовность к сдаче; остальные ошибки не пропускать.

## Защищенный титул и содержание при правках

Сохранить baseline последней пользовательской версии в temp/revision/. Не менять защищенные данные даже при отличиях от config; config не исправлять по титулу без поручения. Использовать отдельные стили основной части, сохранить TOC и его кэш, подогнать начала разделов под сохраненные номера. Word-экспорт запускать с `-PreserveToc -BodyStartHeading "Первый заголовок текущего плана"`. В validate_report.py передать --protected-baseline, в check_revision_layout.py --baseline, текущие --plan/--manifest и окончательный --pdf. Сравнить XML защищенной части и изображения первых страниц с baseline. Конфликты описать без изменения защищенных страниц. Контактные данные и пиксели скриншотов не редактировать как обычный текст документа.
